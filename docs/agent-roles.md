# 에이전트 역할 정의

> Discord 명령 기반 운영에서 각 에이전트의 책임을 분리해, 작업 배분과 검토가 흔들리지 않도록 한다.

## 문서의 목적

이 문서는 "누가 무엇을 하는가"를 정의한다. 역할이 불명확하면 작업 속도는 빨라 보일 수 있어도, 검토와 책임 추적이 무너진다.

## 역할 설계 원칙

- 하나의 역할은 하나의 책임 축을 가진다.
- 역할명은 기능보다 의무를 설명한다.
- 역할 간 경계는 명확해야 한다.
- 한 에이전트가 여러 역할을 맡을 수는 있지만, 동시에 여러 역할의 기준을 섞어서는 안 된다.

## Phase 1 권장 최소 역할

초기에는 아래 4개만으로 시작하는 것을 권장한다.

### 1) Orchestrator / 총괄

- 전체 목표를 작업 단위로 나누고 순서를 정한다.
- 에이전트 배치와 우선순위를 결정한다.
- 진행 중 충돌이나 범위 이탈을 조정한다.

핵심 문장:
> 총괄 역할은 답을 많이 쓰는 사람이 아니라, 팀이 같은 방향으로 움직이게 만드는 사람이다.

### 2) Builder / 구현 담당

- 실제 산출물을 작성한다.
- 문서, 코드, 설정, 실행 결과물을 생성한다.
- 계획에 맞춰 빠르게 실행하고, 막히면 즉시 보고한다.

핵심 문장:
> 구현 역할은 아이디어를 실행 가능한 형태로 바꾸는 데 집중한다.

### 3) Reviewer / 검토 담당

- 산출물의 정확성, 일관성, 누락을 확인한다.
- 요구사항과 결과가 일치하는지 검증한다.
- 수용 여부와 수정 포인트를 명확히 남긴다.

핵심 문장:
> 검토 역할은 "좋아 보인다"가 아니라 "요구를 충족한다"를 판정한다.

### 4) Recorder / 기록 담당

- 의사결정, 명령, 결과를 짧고 명확하게 정리한다.
- 나중에 다시 이어서 작업할 수 있도록 맥락을 보존한다.
- 회고와 재사용을 위한 기록을 남긴다.

핵심 문장:
> 기록 역할은 작업을 끝내는 순간부터 다음 작업을 준비하는 역할이다.

## 확장 역할

프로젝트가 커지면 아래 역할을 추가한다.

### 5) Planner / 계획 담당

- 요청을 실행 가능한 작업 목록으로 바꾼다.
- 필요한 전제, 리스크, 의존성을 정리한다.
- 작업 시작 전에 범위와 완료 조건을 확정한다.

핵심 문장:
> 계획 역할은 일을 시작하게 만드는 역할이 아니라, 일을 끝낼 수 있게 만드는 역할이다.

### 6) QA / 품질 확인 담당

- 실패 경로와 예외 상황을 점검한다.
- 사용자가 실제로 겪을 문제를 찾아낸다.
- 운영 중 재발 가능성이 있는 부분을 우선 탐지한다.

핵심 문장:
> QA 역할은 정답을 확인하는 것이 아니라, 깨질 수 있는 지점을 먼저 찾는 것이다.

### 7) Ops / 운영 담당

- Discord 채널, 명령 규칙, 실행 환경을 관리한다.
- 운영 중 장애와 권한 문제를 처리한다.
- 템플릿이 실제로 돌아가도록 환경을 유지한다.

핵심 문장:
> 운영 역할은 기능을 만드는 사람이 아니라, 기능이 계속 작동하도록 지키는 사람이다.

## 역할 배치 기준

- 새 프로젝트 시작: Orchestrator + Builder + Recorder
- 문서/기능 검토: Reviewer + QA
- 운영 안정화: Ops + Reviewer
- 복잡한 작업: Orchestrator가 전체를 조정하고 Builder/QA를 분리

## 권한과 책임

- 요청을 접수한 역할은 반드시 상태를 갱신한다.
- 검토 역할은 수정 요청 사유를 구체적으로 적는다.
- 총괄 역할은 범위 변경을 승인하거나 되돌린다.
- 기록 역할은 최종 결과와 결정 사항을 한 줄로 요약한다.

## 핸드오프 규칙

역할 전환 시 다음 3가지를 넘긴다.

1. 현재 상태
2. 남은 일
3. 막힌 점

중간 산출물은 다음 역할이 바로 쓸 수 있는 형태여야 한다.
