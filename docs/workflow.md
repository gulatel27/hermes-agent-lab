# 작업 흐름

> Discord 명령으로 요청을 접수하고, 계획하고, 실행하고, 검토하고, 종료하는 표준 흐름.

## 문서의 목적

이 문서는 "작업이 실제로 어떻게 흘러가는가"를 정의한다. 대화가 길어지는 것을 막고, 매번 같은 방식으로 시작/종료할 수 있게 만든다.

## 기본 원칙

- 명령은 시작점이다.
- 작업 상태는 항상 보여야 한다.
- 검토 없이 완료하지 않는다.
- 마지막 메시지는 결과와 다음 액션을 포함해야 한다.

## 표준 상태 흐름

`REQUESTED -> PLANNED -> IN_PROGRESS -> REVIEWING -> DONE`

실패 시에는 `BLOCKED` 또는 `NEEDS_REVISION`으로 전환한다.

## 상태별 정의

### 1) REQUESTED

사용자가 Discord 명령으로 작업을 요청한 상태다.

필수 확인 항목:
- 목표는 무엇인가
- 완료 기준은 무엇인가
- 누가 확인할 것인가
- 어떤 제약이 있는가
- 마감 시점이 있는가

### 2) PLANNED

요청을 실행 가능한 단계로 나눈 상태다.

필수 산출물:
- 작업 목록
- 역할 배정
- 위험 요소
- 검토 포인트

### 3) IN_PROGRESS

Builder가 실제 산출물을 만드는 상태다.

원칙:
- 속도보다 추적 가능성이 중요하다.
- 입력과 출력이 섞이지 않도록 한다.
- 막히면 바로 보고한다.

### 4) REVIEWING

Reviewer와 QA가 요구사항 충족 여부를 확인하는 상태다.

완료 조건:
- 요구사항과 결과가 일치해야 한다.
- 누락이 없어야 한다.
- 재작업이 필요하면 이유가 명확해야 한다.

### 5) DONE

작업이 종료되고 기록까지 남은 상태다.

종료 보고에는 다음 4가지만 간단히 적는다.
- 무엇을 했는가
- 무엇이 만들어졌는가
- 무엇이 막혔는가
- 다음에 무엇을 할 것인가

## Discord 명령 스키마

실제 명령명은 구현 상황에 맞게 조정할 수 있지만, 의미는 아래 기준을 유지한다.

### `/request`

작업을 접수한다.

필수 필드:
- `title`
- `goal`
- `owner`
- `deadline` 또는 `none`
- `constraints`
- `acceptance`

### `/plan`

작업 계획을 생성한다.

필수 필드:
- `request_id`
- `scope`
- `steps`
- `roles`
- `risks`

### `/do`

실행을 시작한다.

필수 필드:
- `plan_id`
- `builder`
- `work_items`

### `/review`

검토를 요청한다.

필수 필드:
- `artifact`
- `reviewer`
- `checklist`

### `/done`

최종 완료를 보고한다.

필수 필드:
- `result`
- `changes`
- `risks_remaining`
- `next_step`

### `/handoff`

다른 역할이나 에이전트에게 넘긴다.

필수 필드:
- `from`
- `to`
- `state`
- `open_items`

## 메시지 작성 규칙

- 한 메시지에는 하나의 목적만 담는다.
- 상태 변경은 눈에 띄게 표시한다.
- 긴 설명보다 실행 가능한 항목을 먼저 쓴다.

## 예외 처리

- 요청이 불명확할 때: 질문을 먼저 하고 시작하지 않는다.
- 작업이 막혔을 때: 원인, 시도한 방법, 필요한 도움을 함께 보고한다.
- 범위가 바뀔 때: 계획을 다시 쓴다.
- 검토에서 실패할 때: 실패 사유를 기준 문장으로 남기고 다시 실행한다.

## 완료 정의

다음 조건을 모두 만족해야 작업이 끝난 것으로 본다.

- 산출물이 요청과 일치한다.
- 검토 기준을 통과했다.
- 재현 가능한 형태로 기록이 남아 있다.
- 다음 사람이 이어서 볼 수 있다.

## 운영 체크리스트

- 요청이 명확한가
- 역할이 지정되었는가
- 완료 기준이 적혀 있는가
- 검토 책임자가 있는가
- 결과가 기록되었는가
